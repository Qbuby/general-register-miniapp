# 实现总结

## 一、起点：仓库是空的

任务书要求「如果当前项目已经存在，不得绕过现有架构另起一套」。
实际情况是 `D:\program\general-register-miniapp` 是一个**完全空的目录**——
没有代码、没有 git 仓库、没有 package.json。因此没有可复用的既有架构，
全部内容为本次实现。技术选型从零决定：

| 选择 | 理由 |
| --- | --- |
| Node.js + TypeScript + Fastify | 团队熟悉、类型安全、生态稳定 |
| `node:sqlite`（Node 22.5+ 内置） | 零原生依赖、零编译，`npm install` 不会因为 node-gyp 失败 |
| 原生微信小程序（无构建步骤） | 导入开发者工具即可运行，不需要额外构建链 |
| 手写 SQL + 迁移文件 | 名额控制需要精确控制事务边界，ORM 的抽象反而碍事 |

依赖只有 3 个运行时包：`fastify`、`zod`、`qrcode`。

## 二、二维码方案是怎么定的

任务书要求「不能用一个看似成功但实际不能扫码访问的假二维码替代正式功能」，
同时又要求在没有微信凭据时不能直接罢工。实现上做成**双模式 + 显式标注**：

- 配置了 `WX_APPID` / `WX_APPSECRET` → 走官方 `getwxacodeunlimit`，真小程序码；
- 未配置 → 生成指向服务端预览页的码，但**在三个地方都标注它不是小程序码**：
  接口返回 `mode: "preview"` + `warning`、PNG 响应头 `X-QR-Mode: preview`、
  小程序工作台页面显示黄色提示条；生产环境直接 503。

预览页读的是同一个数据库、渲染的是公众真正会看到的内容，所以扫码 → 落地 →
填表 → 提交落库这条链路可以被完整验证，而不是只能验到「图片能生成」。

分享码**一经生成永不更换**，「刷新二维码」只重新出图——这样印在海报上的码
不会因为后台任何操作而失效。

## 三、从参考项目借鉴了什么

先读了指定仓库的源码（不是 README），提取设计而非代码。

### WeGongYi（无许可证文件 —— 仅作设计研究，未复制任何代码）

- **`mark` 稳定字段标识**：表单字段带一个随机 10 位 key，而不是用显示名当身份。
  本项目落成 `form_fields.field_key`，并在注释里写明「改名不改 key」。
- **`min`/`max` 一对约束**：用它同时表达「最多 10 个字符」和「至少选 2 项」。
  本项目落成 `minLength`/`maxLength`（多选时复用为选中项数的上下限）与
  `minValue`/`maxValue`。
- **管理端二维码把目标页面路径传给云函数**：说明二维码只承载入口，
  状态必须在扫码时重新判定——这一点本项目完整实现。

### OPENPASS（AGPL-3.0 —— 仅作设计参考，未复制代码）

- **锁定 → 判状态 → 判名额 → 判重复 → 插入**的顺序。本项目用
  `BEGIN IMMEDIATE` 实现同样的串行化，`src/services/registrations.ts` 里
  注明了 Postgres 下对应 `SELECT ... FOR UPDATE`。
- **人数上限比对计数器而不是 `COUNT(*)`**，且计数器与插入在同一事务内维护。
- **唯一键冲突翻译成业务结果**而不是 500（`isUniqueViolation` → 「已报名过」）。
- **表单字段用数据库 CHECK 约束 + 唯一索引固定类型和顺序**，本项目在
  `001_init.sql` 里对字段类型、状态取值都加了 CHECK，顺序加了唯一索引。

### Regista（无根目录 LICENSE —— 仅作设计参考，未复制代码）

- **每次请求重新读数据库确认成员关系**，token 只承载身份。
  本项目的 `requireMembership()` 照此实现，并加了 `users.token_version`
  以便一次性作废全部 token。
- **跨租户访问返回 404 而不是 403**，避免通过状态码探测资源是否存在。
- **租户过滤写在查询内部**（`WHERE id = ? AND organization_id = ?`），
  而不是先查后判。本项目所有涉及项目的查询都是这个写法。
- **导出加审计日志**、**导出响应 `Cache-Control: no-store`**、CSV 中和
  `= + - @` 开头的单元格。本项目全部采用。

### Hi.Events（AGPL-3.0 + 署名要求 —— 仅作产品交互参考）

只参考了公开详情页的信息层次、报名者列表与搜索的交互形态。没有引入其票务、
收费、签到体系。

### lms-front（MIT —— 唯一可合法复用的仓库）

只参考了多租户隔离思路，未复制代码。

### cloud-TA

按任务书要求，明确**没有**以它为基础，也没有引入排课、课时账务、财务。

## 四、本项目相对参考项目补强的一处

调研中发现一个共性缺口：**被参考的三个项目都没有给报名记录保存表单快照**，
只是把答案存成一份不透明的 JSON，而表单定义又是整体替换的
（OPENPASS 的 `SetFormFields` 直接删掉重建）。结果是：字段一改名，
历史报名记录就失去可读性。

任务书明确要求「后续机构修改表单不能改变历史报名数据的含义」。本项目的做法：

1. `registrations.form_snapshot` 保存提交当时整份表单定义
   （key + label + type + required + options）；
2. `registrations.answers` 按 `field_key` 索引，而不是按数组下标——
   顺序变化不会让答案错位；
3. 删除字段只影响后续表单，历史记录仍然带着当时的标签和答案；
4. 导出时如果发现某个已删除字段在历史记录里出现过，自动补一列
   「字段名（历史）」。

`test/registration.test.ts` 与 `test/export.test.ts` 各有一条用例专门验证这条。

## 五、多租户是怎么保证的

不是靠前端隐藏按钮，而是三层：

1. **接口层**：所有 `/api/orgs/:orgId/*` 先过 `requireMembership()`；
2. **查询层**：SQL 本身带 `organization_id` 条件，不存在「查出来再判」的窗口；
3. **数据层**：二维码图片接口同样鉴权；报名记录表自带 `organization_id`，
   删除机构时级联清理。

跨租户一律返回 404 而非 403，因为 403 本身就泄露了「这个机构存在」。

## 六、动态报名表是怎么做到机构不用写代码的

- 项目编辑页内置**构建器**：增删字段、选类型、设必填、调顺序、写选项，
  外加三套常用模板（成人自报 / 家长为孩子报 / 团体报名）。
- 字段类型 8 种：单行文本、多行文本、手机号、数字、单选、多选、下拉、日期。
- 公众端由**同一个组件** `components/form-field` 按后端下发的字段定义渲染，
  新增字段类型不需要改小程序代码。
- 校验规则在 `src/lib/form.ts`（服务端权威）和 `miniprogram/utils/form.js`
  （即时反馈）各实现一份，规则一致，注释里互相指明「服务端会重新校验」。
- 字段顺序由服务端按数组下标分配，客户端不传顺序。

开发过程中实际修掉的几个问题，记录在此以免遗漏：
- 报名记录插入语句的参数个数与列数不匹配（新增 `receipt_code` 列）；
- Zod `.superRefine()` 产生 `ZodEffects`，没有 `.partial()`，需要单独定义 patch schema；
- 表单字段组件自定义了 `triggerEvent`，会覆盖框架同名能力并导致无限递归；
- WXML 里写了数组字面量作为 picker 的 `range`（WXML 不支持这种表达式）；
- **预览页表单提交地址同时丢了路径前缀 `/p/` 和 `?t=` 令牌**，
  会导致提交必然 403/404——这个是靠浏览器实际点击提交才发现的；
- **`tsc` 不会复制 `.sql` 迁移文件**，编译产物启动即崩；已加 `scripts/copy-assets.mjs`，
  并把「用 `dist/index.js` 实际启动一次」纳入验证；
- **生产模式下二维码元数据接口仍返回 200 + `mode: "preview"`**，
  与图片接口的 503 自相矛盾；已统一，并补了 `test/qr-production.test.ts`。

## 八、明确没做的

按任务书，首版不做：在线支付与退款、复杂教务与课时核销、直播录播、
AI 生成内容、多级分销返佣、审批流与签到核销、独立 App、
为每家机构单独开发小程序、独立 PC 管理系统。

数据模型上为多成员留了位置（`organization_members` + 三级角色），
但首版只实现了「创建者即 owner」，没有邀请/加入界面。
