## 一、自动化测试（`npm test`，107 项）

```
test/helpers.ts         每个测试文件独立的临时库与会话辅助
test/tenancy.test.ts    多租户隔离
test/registration.test.ts  动态报名表、校验、快照、状态门禁
test/capacity.test.ts   人数上限与并发
test/qrcode.test.ts     二维码稳定性与目标映射
test/export.test.ts     导出内容与安全
test/qr-production.test.ts  生产模式下拒绝输出不可用的二维码
test/members.test.ts    成员、角色与邀请
test/miniprogram-form.test.ts  小程序表单校验与服务端规则的一致性
test/edge-cases.test.ts 边界与异常场景（并查 bug 用）
test/qr-decode.test.ts  把二维码 PNG 真正解码回文本
```

每个测试文件在**独立进程**中运行，各自使用独立的临时数据库，可单独运行：

```bash
npx tsx --test test/tenancy.test.ts
```

### 关键用例

**多租户隔离**（`tenancy.test.ts`，13 项）
机构 B 逐个尝试访问机构 A 的机构资料、项目列表、项目详情、报名记录、导出、
报名状态修改、报名表、二维码；另有用例把机构 B 的 orgId 和机构 A 的 projectId
拼在一起，确认查询层的 `AND organization_id = ?` 拦得住。未登录与伪造 token 同样被拒。

**历史数据不被改写**（`registration.test.ts`）
提交一条报名 → 把表单改成「换标签 + 换顺序 + 删一个 + 加一个」→ 重新读取该记录，
断言姓名、电话、答案键值、以及快照里的字段名全部与提交时一致。

**并发名额**（`capacity.test.ts`）
5 个名额，同时发起 30 次提交（每次幂等键不同，因此不能靠幂等去重），
断言恰好 5 条 201、25 条 409 且 code 为 `project_full`，并且数据库中的实际条数是 5。

**导出**（`export.test.ts`）
验证表头含固定列与动态列、多选答案完整导出、已删除的历史字段仍以「（历史）」列导出、
以 `=` 开头的内容被转义、导出行为写入审计日志。

**二维码**（`qrcode.test.ts`）
验证 PNG 魔数、图片体积、目标页面路径、重复获取不换码、已下架项目扫码仍返回 200
并说明原因、把有效分享码拼到工作台接口后面拿不到任何数据。

## 二、小程序静态检查

```bash
node scripts/check-miniprogram.mjs
```

开发者工具不在 CI 里，但很多低级错误可以静态查出来：

- `app.json` 里声明的每个页面是否四件套齐全（`.js` `.json` `.wxml` `.wxss`）；
- 所有 JSON 是否可解析；
- WXML 里 `bind*` / `catch*` 绑定的事件名，在对应 JS 里是否存在同名方法
  （排除微信原生事件）；
- `usingComponents` 指向的组件路径是否存在（自动尝试省略的扩展名）。

这个检查在开发中确实抓到过问题：表单类型选择器原本在 WXML 里写了数组字面量
`range="{{['text','textarea',...]}}"`，WXML 不支持这种表达式，检查脚本在
开发者工具之外先把它暴露了出来。

## 三、端到端冒烟（`npm run smoke`）

```bash
# 终端 1
npm start
# 终端 2
npm run smoke
```

按验收标准逐条走一遍真实 HTTP 流程，输出每项的通过/失败，退出码 0 表示全通过。
它会创建带时间戳的机构与项目，不影响既有数据。

覆盖：服务可用性 → 场景 A（机构创建与隔离）→ B（项目发布与上下架）→
C/D（两级二维码）→ E（动态表单、校验、快照）→ F（报名管理、搜索、导出、
并发名额、截止时间）→ G（预览页与真实数据）。

最近一次运行结果：**54 项全部通过**（含 Docker 容器内实测）。

### 人工验证过的界面

服务启动后用浏览器实际打开预览页确认过：

- 机构主页正确展示机构资料、介绍、在招项目卡片与联系方式；
- 项目详情页按该项目**自己的**表单渲染输入项（课程项目是「学员姓名 / 家长手机号 /
  当前年级 / 是否有编程基础 / 其他说明」，训练营项目是完全不同的一套）；
- 在浏览器中填写并提交，服务端校验通过后写入数据库，返回报名编号与机构联系方式；
- 直接 `curl` 一个必填项缺失的请求，返回 400 且指出具体字段
  （这正是「前端校验不能替代后端校验」的实证）。

## 六、成员与邀请

`test/members.test.ts`（14 项）覆盖：

- owner 生成邀请码；邀请**不能**授予 owner；
- 接受后立即获得对应权限；operator 可查看报名与二维码；
- operator 不能改机构资料、建项目、改报名表、管成员（403）；
- admin 可改资料与建项目，但不能邀请或移除成员（403）；
- 同一邀请码不能被用两次，且失败方不会成为成员；
- 接受需登录；邀请码本身即凭据，不依赖 `orgId`；
- 无效 / 过期 / 已撤销邀请码各自给出明确原因；
- owner 可改角色与移除成员，移除后权限**立即**失效；
- 不能移除自己、不能移除或降级唯一所有者；
- 成员只能看到自己所属机构的数据；
- 空 JSON body 被容忍，但非法 JSON 仍被拒绝。

## 七、前后端表单校验一致性

`test/miniprogram-form.test.ts`（12 项）把小程序端的
`miniprogram/utils/form.js` 与服务端的 `src/lib/form.ts` 放在同一组用例上比对，
任何一端放宽或收紧都会立刻被发现。

**这套测试第一次运行就抓到两处真实漂移**：

1. 多选字段：服务端用 `Set` 去重后再计数，客户端直接按原数组计数。
   选 `['A','B','C','A']` 时服务端判为 3 项通过，客户端判为 4 项报「最多选 3 项」。
2. 日期字段：服务端除格式外还校验日历合法性，客户端只做正则，
   `2016-13-45` 这种不存在的日期会被客户端放行。

两处均以服务端为准修正了客户端。这类不一致正是「用户在前端填得好好的、
一点提交就报错」这类最难排查问题的来源。


## 八、端到端联调发现并修复的问题

这一轮以「找 bug」为目标编写用例，发现并修复了以下问题。

### 1. 二维码从未被真正解码验证

此前所有二维码测试只断言「返回了一张 PNG」「字节数够大」，但这证明不了它
**能被扫出来**——payload 写错、编码不对、对比度不足，字节数都照样正常。

新增 `test/qr-decode.test.ts`（5 项），用独立的解码库（jsQR + pngjs，仅测试期依赖）
把 PNG 反解回文本，断言：

- 机构码解码后确实指向该机构的预览地址；
- 每个项目码指向各自的项目详情，且互不串码；
- 解码出的地址**直接请求就能打开**对应页面；
- 连续三次获取解码结果一致且分辨率均为 1024px；
- 分享码在解码文本中完整无损。

结果：全部通过，产品的核心主张首次得到直接验证。

### 2. 搜索框的 LIKE 通配符注入（真实 bug）

用户在搜索框输入 `%`，因为 `%` 在 SQL `LIKE` 中是「匹配任意」的通配符，
**该机构的全部报名记录都会被列出来**。`_` 同理。这既不符合直觉，
也等于把筛选功能绕过去了。

修复：在 `listRegistrations` 中对反斜杠、百分号、下划线做转义，
并为 LIKE 子句加上 `ESCAPE` 子句指定转义符。
实测修复前后：搜索 `%` 由「命中全部」变为「命中 0 条」，而 `张_三` 这类
含下划线的正常内容仍能精确命中。

### 3. 畸形 JSON 返回 500（真实 bug）

客户端发出格式错误的 JSON 时，Fastify 的解析错误带 400 的 `statusCode`，
但自定义错误处理器只检查 `error.validation`，导致掉进 500 分支——
用户明明发错了请求，却看到「服务器内部错误」。

修复：错误处理器补充识别 4xx 的 `statusCode`，返回可读的 400。

### 4. 一处测试自身的错误假设

测试曾断言「未登录 POST /api/orgs 且参数类型错误 → 400」，实际返回 401。
经核查**代码是对的**：认证检查先于参数校验，不该给未认证调用方泄露校验细节。
已修正测试，分别断言未登录 401、已登录但类型错误 400。
